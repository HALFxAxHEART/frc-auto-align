## 3. How robot code runs (command-based)

WPILib code is organized into **subsystems** and **commands**.

- A **subsystem** is a piece of hardware you control as one unit: the drivetrain, an intake, a shooter.
  It holds the motors and sensors and has small methods like `setSpeed()` or `getPose()`.
- A **command** is an action that uses one or more subsystems: "drive with the sticks", "run the intake",
  "follow this path". A command **requires** its subsystems, so two commands can't fight over the same motor.
  If a new command needs a subsystem that's busy, the old command is **interrupted**.
- A **default command** runs on a subsystem whenever nothing else is using it. The drivetrain's default command is
  "drive with the sticks".
- **Triggers** start commands. Usually a button (`driver.x().whileTrue(...)`), but anything true/false works.

The **Command Scheduler** runs every 20 ms (50 times a second). Each time it:
1. checks the buttons/triggers and starts or stops commands,
2. runs every active command,
3. calls every subsystem's `periodic()`.

The boot order is: `Main` → `Robot()` → `RobotContainer()` → subsystems are made → buttons are bound.

## 4. Field and robot directions

- The field origin (0, 0) is the **blue alliance's right corner**. **+X** points away from the blue driver station,
  **+Y** points left (from the blue drivers' view). Angles are **counter-clockwise positive**. Units are **meters**
  and **radians** (or rotations in CTRE code).
- **Pose** = where the robot is: X, Y and heading.
- **Odometry** = working out the pose from how far the wheels turned and the gyro. Accurate short-term, but drifts.
- **Vision** (AprilTags) corrects the drift. Both are combined by the **pose estimator** in the drivetrain.
- **Field-centric driving**: pushing the stick forward drives away from the driver no matter which way the robot faces.
  Press **Start** to reset "forward" if it gets off.
- PathPlanner paths are drawn on the **blue** side and flipped automatically when we're red.

## 5. How to...

### Build and deploy
WPILib VS Code: `Ctrl+Shift+P` → **WPILib: Deploy Robot Code** (connected to the robot by USB, ethernet or radio).
**WPILib: Build Robot Code** just checks it compiles. Fix every red error before deploying.

### Try code without a robot (simulation)
`Ctrl+Shift+P` → **WPILib: Simulate Robot Code** → pick *Sim GUI*. Drag a keyboard/controller into Joystick 0,
set the mode to Teleoperated, and drive. Open AdvantageScope, connect to `localhost`, and look at the field.

### Change what a button does
`RobotContainer.java` → `configureBindings()`. Example:
```java
driver.leftBumper().whileTrue(roller.runCommand(ExampleRollerConstants.kIntakeRps));
```
Xbox buttons: `a() b() x() y() leftBumper() rightBumper() leftTrigger() rightTrigger() start() back() povUp()...`

### Add a mechanism (intake, shooter, arm...)
1. Give the motor a CAN ID in Tuner X and add it to `Constants.CANIds`.
2. Copy `subsystems/ExampleRoller.java` and rename it. Add its settings section to `Constants.java`.
3. Make it in `RobotContainer`: `public final Intake intake = new Intake();`
4. Bind buttons to its commands in `configureBindings()`.
5. Put its important values on the dashboard in `periodic()` (they're logged automatically).

### Add an autonomous routine
1. Open the PathPlanner app on this project folder. Draw paths, then build an **Auto** from them.
2. Need the robot to do something during the auto (intake, shoot)? Add a **named command** in
   `AutonContainer.registerNamedCommands()` with `register("Name", command)`, then use the same name in PathPlanner.
3. Add it to the dashboard chooser in `AutonContainer.buildAutonChooser()`:
   `chooser.addOption("My Auto", AutoBuilder.buildAuto("My Auto"));` (name = the `.auto` file name).
4. Test it in simulation before the real robot.

### Add another Limelight
You can have as many as you want. Each one adds its own position measurement, and they all work the same way.

**On the Limelight** (plug it into the robot's network, open `http://limelight.local:5801`; with two plugged in,
set them up one at a time, because both start with that same name):
1. **Settings → Hostname:** give it a unique name that starts with `limelight-`, e.g. `limelight-front`,
   `limelight-back`. This name is how the code finds it, so two cameras can never share one.
2. **Settings → IP address:** set a unique static IP. Limelight recommends `10.TE.AM.11` to `.19`, so for 5090: `10.50.90.11` for the first, `.12` for the second, and so on.
3. **Pipeline:** set up an AprilTag pipeline (the image settings: exposure, resolution, tag family, field map).
   Then **export the pipeline file** and save it in this repo's `limelight/` folder as a backup.
4. Update the firmware (LLOS) to the 2026 version if it's old (Limelight Hardware Manager).

**In the code** (`Constants.java` → `VisionConstants.kCameras`):

5. Measure where the camera is mounted, from the **center of the robot on the floor**:
   forward/back (m), left/right (m), height (m), tilt up/down (deg), which way it faces (deg).
6. Add one line:
   ```java
   Camera.configuredInCode("limelight-back", 0, new CameraPose(-0.30, 0.0, 0.25, 0, 20, 180)),
   ```
   = named `limelight-back`, pipeline 0, 30 cm behind center, centered, 25 cm up, tilted up 20°, facing backward.
7. Deploy. On the dashboard check `Vision/limelight-back/Connected`. Then put the robot where it can see a tag, and
   check that `Vision/limelight-back/Correction (m)` is small and the robot appears in the right place on the field.
   If the pose is way off or mirrored, the mount numbers are wrong. The usual mistake is the yaw sign or using cm instead of m.

#### What goes in code vs. on the Limelight?
| Setting | Where | Why |
|---|---|---|
| Camera name list | **Code** (`kCameras`) | The code needs to know which cameras to read. |
| Mount position (Robot Space Pose) | **Code** (`configuredInCode`) | It's part of the robot, so it belongs in git. It comes back automatically if a camera is swapped or reflashed, and changes show up in reviews. Code **overrides** the web page. |
| Which pipeline to run | **Code** | Same reason. |
| Image settings (exposure, resolution, tag family, field map, crop) | **Limelight web page** | You tune these while watching the live camera feed. Back up the exported pipeline file in `limelight/`. |
| Hostname and IP address | **Limelight web page** | The camera needs them before the code can even talk to it. |

`Camera.configuredOnLimelight("name")` means "use whatever's saved on the camera". It's only for a camera whose
mount position hasn't been measured into code yet.

### See what happened in a match
Plug the USB stick into a laptop and open the `.wpilog` in AdvantageScope. See `LOGGING.md`.

## 6. CTRE basics

- **Phoenix 6** is CTRE's library. Our motors are **TalonFX** (Kraken X60), the gyro is a **Pigeon 2**, the swerve
  angle sensors are **CANcoders**.
- Every CTRE device has a **CAN ID** and a **CAN bus**. Wrong ID or bus = it silently doesn't work.
  Always check IDs in Tuner X against `Constants.java` / `TunerConstants.java`.
- **Current limits** keep motors from overheating and the battery from browning out (the robot resets when voltage
  drops below ~6.75 V). Every motor gets stator and supply limits. Watch out: `kSlipCurrent` in TunerConstants
  becomes the drive motors' current limit.
- **FOC** is a stronger, smoother way to drive the motors. It needs Phoenix Pro, which we have. Use `.withEnableFOC(true)`.
- Motors are controlled with **control requests**: `VelocityVoltage` (hold a speed), `PositionVoltage` /
  `MotionMagicVoltage` (go to a position), `DutyCycleOut` (just a % of power), `NeutralOut` (stop).
  Make each request once and reuse it.

## 7. Words you'll hear

| Word | Meaning |
|---|---|
| **AprilTag** | Square barcode on the field. The camera knows exactly where each one is. |
| **MegaTag1 / MegaTag2** | Limelight's two ways to work out the robot's pose. MT2 uses our gyro for heading and is steadier. |
| **CAN** | The network cable (yellow/green wires) connecting motors and sensors to the roboRIO. |
| **CANivore** | A USB adapter that adds a faster CAN bus. Ours is named "Jarvis". |
| **PDH** | Power Distribution Hub: the breakers that power everything. |
| **roboRIO** | The robot's main computer. Runs this code. |
| **Brownout** | The battery voltage drops too low and the roboRIO turns motors off. Usually too much current. |
| **PID** | Feedback control: push harder the further you are from the target. kP, kI, kD are the "how hard" numbers. |
| **Feedforward (kS, kV, kA)** | The volts you already know you'll need (to overcome friction, to hold a speed). PID only fixes what's left. |
| **Setpoint** | The target (a speed, a position). |
| **Deadband** | Ignore tiny stick movements so a resting stick doesn't make the robot creep. |
| **Std dev (standard deviation)** | How much to trust a measurement. Smaller = trust it more. |
| **NetworkTables (NT)** | How the robot shares values with dashboards. Everything on NT gets logged. |
| **Odometry** | Tracking position from wheel movement + gyro. |
| **SysId** | A WPILib tool that measures a mechanism to work out its feedforward/PID gains. |

## 8. Naming: keep it professional

Our code is read by judges, mentors, alumni and other teams (it's public on GitHub, and award judges ask about it).
**Every name should tell a stranger exactly what the thing is.** No jokes, nicknames, memes or inside references
in class names, method names, variables, commands, dashboard keys, branch names or commit messages.

| Instead of | Write |
|---|---|
| `Yeeter`, `BigBoi` | `Shooter`, `Elevator` |
| `doTheThing()`, `stuff()` | `feedWhenReady()`, `runIntake()` |
| `bob`, `m1`, `motor2` | `leftFlywheelMotor`, `pivotMotor` |
| `Constants.x`, `val = 16.1` | `IntakeConstants.kDeployedPositionRotations = 16.1` |
| Dashboard `"111 pose X"`, `"aaa"` | `"Drive/Pose X (m)"` |
| Branch `fun-stuff`, `my-branch` | `intake-tuning`, `auto-left-two-piece` |
| Commit `"fixed it"`, `"lol"` | `"Lower intake current limit to 30 A (was tripping breaker)"` |

Naming style (standard Java, so everyone can read it):
- **Classes**: `PascalCase` nouns: `Intake`, `ShooterConstants`, `AutonContainer`.
- **Methods**: `camelCase` verbs: `setSpeed()`, `getPose()`, `isAtSetpoint()` (booleans start with `is`/`has`/`at`).
- **Commands** (methods that return a Command): say the action: `intakeCommand()`, `driveToScoringPose()`.
- **Constants**: `k` + `PascalCase` + **units** where it's a number: `kMaxSpeedMetersPerSecond`, `kIntakeRps`.
- **Member variables**: `m_` + `camelCase` is fine (`m_motor`), just be consistent within a file.
- **Dashboard keys**: `Subsystem/Thing (units)`, e.g. `Shooter/Velocity (RPS)`. The same names end up in the logs.
- **No abbreviations nobody else knows.** `ll` is fine for Limelight; `tgtDstFltr` is not.

Code reviews (pull requests) should send a name back if it doesn't pass the "would a judge understand this?" test.

## 9. Team rules for code

1. **Work on a branch**, not `main`. Name it after what you're doing. Pull before you start, push when done.
2. **No magic numbers.** Numbers go in `Constants.java` with a comment saying what it is and its units.
3. **Comment the WHY**, not the what. "Limit 60 A because 120 A browned us out" beats "set limit to 60".
4. **Check CAN IDs in Tuner X** before blaming the code. A wrong ID was behind a whole week of 2026 bugs.
5. **Test in simulation first**, then on the robot on blocks (wheels off the ground), then on the floor.
6. **Something weird happened? Check the log before changing code.** (See LOGGING.md.)
7. **Professional, descriptive names only** (see section 8). Code is reviewed by judges, alumni and other teams.
8. **Don't edit generated files** (`TunerConstants.java`, `LimelightHelpers.java`) unless you have to. If you do, comment why.
